### วิธีใช้ตอนเขียนเล่ม

1. บทที่ 1 กับบทที่ 3 ส่วนใหญ่*ลอก*มาจาก proposal —
   **ห้ามลอกประโยคที่ทะเบียนนี้ทำเครื่องหมายว่าเปลี่ยนแล้ว**
   ให้เขียนใหม่ตามของจริงพร้อมใส่หมายเหตุลงวันที่
2. บทที่ 5 (อภิปราย/ข้อจำกัด) หยิบแถวที่เป็น **ลดขอบเขต** และ **เลื่อนออกไป**
   ไปใช้ได้เกือบตรง ๆ
3. **ห้ามเขียนว่า proposal บอกในสิ่งที่มันไม่ได้บอก** เกณฑ์หรือข้ออ้างไหน
   ที่มาจากเราไม่ใช่จาก §1.3 มีระบุไว้แล้วใน `docs/KPI_SPEC.md` และต้องคงไว้

### ประเภทของส่วนต่าง

| ประเภท | ความหมาย |
|---|---|
| **เปลี่ยนตัวแทน** | งานเดิม แต่ใช้เครื่องมือ/กลไกคนละตัว |
| **ลดขอบเขต** | สิ่งที่วางแผนไว้ไม่ได้สร้าง หรือสร้างเล็กลง |
| **ขยายขอบเขต** | สร้างสิ่งที่ proposal ไม่ได้วางแผนไว้ |
| **ใช้แผนสำรอง** | แผนสำรองที่ proposal ประกาศไว้เองถูกใช้จริง |
| **proposal ขัดกันเอง** | เอกสารเขียนขัดกันสองที่ ของจริงทำตามข้างหนึ่ง |
| **ข้ออ้างที่ยังไม่ตรวจ** | proposal อ้างคุณสมบัติที่ยังไม่มีใครตรวจกับของจริง |
| **ทำตามแล้ว** | ใส่ไว้เพราะผู้อ่านจะมองหา และควรเจอว่ายืนยันแล้ว |
| **build ขยับหลังวัด** | วัด KPI ตามแผนแล้ว แต่ UI ที่ถูกวัดเปลี่ยนไปหลังจากนั้น |

## §2 ส่วนต่างที่ไปขยับตัวเลขที่ KPI รายงาน

ทุกข้อข้างบนสำคัญในแง่ความซื่อตรง **แต่สามข้อนี้ไปเปลี่ยนผลการวัด**
จึงต้องอยู่ข้างผลลัพธ์ ไม่ใช่อยู่แค่ในหัวข้อขอบเขต

### D-10 · ข้อจำกัด free tier คือผู้ต้องสงสัยอันดับหนึ่งของ KPI-4 และ KPI-5

`docs/KPI_FAILURE_ANALYSIS.th.md` พิสูจน์ว่าบน `/dashboard` ทุกตัวชี้วัดฝั่ง
หน้าเว็บได้เต็มหมด (TBT 30/30 · CLS 25/25 · FCP 10/10) และแต้มที่หายไปทั้งหมด
คือ "ข้อมูลมาถึงจอช้า" · และภายใต้ผู้ใช้ 50 คนพร้อมกัน
**ทุกขั้นที่แตะฐานข้อมูลชนเพดาน timeout 60 วินาที ในขณะที่ขั้นเดียวที่ไม่แตะ
ฐานข้อมูลไม่เคยพังเลย**

**proposal ผูกมัดโปรเจกต์ไว้กับ free/hobby tier ตั้งแต่หน้า 11–12** ซึ่งมีผล
สองข้อที่ต้องเขียนลงเล่ม:

1. **ความล้มเหลวนี้เป็นผลจากข้อจำกัดที่ประกาศไว้ในการออกแบบ** ไม่ใช่อุบัติเหตุ
   — ประโยคนี้แข็งกว่า "ระบบช้า" มาก และเป็นความจริงที่อ้างอิงได้
2. **ทางแก้ A ในบทวิเคราะห์ (ขยายชั้นของฐานข้อมูล) คือการออกจากข้อจำกัดนั้น**
   ถ้าทำ ต้องบันทึกที่นี่ว่าเป็นส่วนต่างอีกข้อ พร้อมวัด before/after ทั้งสองฝั่ง

### D-7 · เส้นทาง ingestion ที่ถูกวัด คือแผนสำรองของ proposal ไม่ใช่แผนหลัก

KPI-2 (20/20) และ KPI-3 (12/12) วัดบน **PostgREST staging + `promote_batch` RPC**
ซึ่งคือแผนสำรอง "Thin-Backend" ของ §3.5 · ผู้อ่านที่เข้าใจว่าผลสองตัวนี้ยืนยัน
สถาปัตยกรรม Airflow ในหน้า 19 จะเข้าใจผิด **Airflow สร้างจริงและถูกใช้งานโดยชุด
ทดสอบในเครื่อง แต่ไม่ได้ deploy และไม่ใช่สิ่งที่ KPI ingestion สองตัวที่ผ่านวัด**

### D-14 · สามในเจ็ดเกณฑ์เป็นของเรา ไม่ใช่ของ proposal

เปิดเผยไว้แล้วใน `docs/KPI_SPEC.md` และเขียนซ้ำตรงนี้เพราะเป็นเรื่องที่พลาด
ง่ายที่สุดตอนตอบปากเปล่า: **Lighthouse ≥ 80 · 50 concurrent users · SUS ≥ 68
เป็นของ proposal ส่วน MAPE 0.5% · p95 2 วินาที · error 1% · และ 100% ของ
ingestion เป็นของเรา**
