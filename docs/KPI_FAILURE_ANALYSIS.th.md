## §2 KPI-4 — Lighthouse Performance ≥ 80 (desktop)

### ขั้น 1 · แนวคิดและทฤษฎีที่ใช้ออกแบบ

**เกณฑ์:** ≥ 80/100 — มาจาก proposal §1.3 โดยตรง (Class 1)

**เครื่องมือ:** Google Lighthouse ซึ่งให้คะแนนจากตัวชี้วัด Core Web Vitals
5 ตัวถ่วงน้ำหนักกัน — LCP 25% · TBT 30% · CLS 25% · FCP 10% · Speed Index 10%
เลือกเพราะเป็นมาตรฐานอุตสาหกรรมที่ผู้อ่านตรวจซ้ำได้ ไม่ใช่ตัวเลขที่เรานิยามเอง

**โปรโตคอลที่ล็อกไว้ก่อนวัด:** 3 เส้นทาง (`/`, `/dashboard`, `/imports`) ×
2 preset × 6 รอบ ทิ้งรอบแรก ใช้ median ของรอบ 2–6 · **ทุกเส้นทางต้อง ≥ 80
ตกเส้นเดียวคือตกทั้ง KPI** (กันไม่ให้ค่าเฉลี่ยเอาหน้า Landing มาอุ้ม Dashboard)

**⭐ สมมติฐานที่เขียนไว้ก่อนวัด:** สเปกระบุผู้ต้องสงสัยไว้ล่วงหน้าว่าคือ
**ขนาดไฟล์ JavaScript (entry chunk 919 kB)** และทางแก้คือ route-level code
splitting ตามทฤษฎีมาตรฐานของ SPA ที่ว่า bundle ใหญ่ทำให้ผู้ใช้รอนาน
**การเขียนผู้ต้องสงสัยลงไปก่อนวัด คือสิ่งที่ทำให้พูดได้ทีหลังว่าการวัดหักล้างมัน**

### ขั้น 3 · วิธีแก้ที่เลือก และเหตุผล

**หลักการที่ใช้:** ลดจำนวน round trip ต่อการเปิดหน้าหนึ่งครั้ง โดยไม่เปลี่ยน
พฤติกรรมที่ผู้ใช้เห็น — สามเทคนิค

1. **Request deduplication** — คำขอที่เกิดพร้อมกันและเหมือนกันทุกประการ ให้ยิงจริง
   ครั้งเดียวแล้วแบ่งคำตอบกัน (`/auth/v1/user` 30 → 3)
2. **Single source of truth ผ่าน React Query** — 6 hook เคยต่างคนต่างถามว่า
   "ตอนนี้อยู่ workspace ไหน" → รวมเป็นคำตอบเดียวที่ใช้ร่วมกัน
3. **Opt-in / lazy fetching** — ข้อมูลที่มีที่ใช้จริงแค่หน้าเดียว
   (`business_types`, `industries`) เลิกดึงในทุกหน้า · เมนูซ้ายเคยลากข้อมูล
   ทั้งทีมมาเพื่อ**แสดงตัวเลขตัวเดียว** → แยกออกเป็น query เล็ก

รวม **7 commits** (`536c50b` … `29a88bb`)

**ทำไมไม่เลือกวิธีอื่นในรอบนี้:** ทางแก้ที่ตรงต้นเหตุกว่าคือยุบคำขอหลายสิบตัวให้
เหลือ 1–2 ตัวฝั่งเซิร์ฟเวอร์ (RPC) แต่ต้องรื้อ RLS และเขียนเทสต์ใหม่ทั้งชุด
รอบนี้เลือกทำเฉพาะข้อที่**ความเสี่ยงต่ำและตรวจสอบได้ทีละก้อน**ก่อน
เพื่อให้รู้ว่า "การลดจำนวนคำขออย่างเดียว" ให้ผลเท่าไหร่ — ซึ่งเป็นคำตอบที่
มีค่าในตัวเอง ไม่ว่าจะผ่านหรือไม่ผ่าน

| LCP ลดลงมาก | **H1 ถูก** — ตันที่ความจุ | รายงานว่าเป็นข้อจำกัดของสภาพแวดล้อม ไม่ใช่ของสถาปัตยกรรม |
| LCP แทบไม่ขยับ | **H2 ถูก** — เราถล่มตัวเอง | ทำ B ต่อ โดยมีหลักฐานรองรับว่าทำไมต้องทำ |
| ลดบ้างแต่ไม่ถึงเกณฑ์ | ทั้งคู่มีส่วน | ต้องทำทั้ง A และ B ซึ่งเป็นข้อสรุปที่มีค่าในตัวเอง |

**ไม่ว่าผลออกทางไหน บทที่ 5 ก็มีข้อสรุปที่ยืนได้** และนั่นคือเหตุผลที่การทดลอง
นี้คุ้มค่าจะทำ ต่างจากการไล่แก้ไปเรื่อย ๆ จนกว่าตัวเลขจะสวย
